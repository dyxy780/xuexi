# 冒烟测试与回归测试指南

目的：
- 冒烟测试：在新版本发布或构建后快速验证核心功能是否可用，决定是否进入更深层次的测试。
- 回归测试：在缺陷修复或功能变更后，验证修改没有引入新的缺陷，确保核心业务流程稳定。

冒烟测试（Smoke Test）：
- 特点：面向核心路径、快速、可在几分钟到半小时内完成。
- 包含内容示例：
  - 应用能启动/部署成功
  - 核心登录/鉴权流程验证
  - 关键业务操作执行（下单、查询、支付等）
  - 主要页面能正常加载
- 执行时机：每次构建/部署后优先执行。
- 通过标准：所有关键点通过或只有非阻塞性问题；若出现阻塞性问题需阻止发布并通知开发。

回归测试（Regression Test）：
- 特点：覆盖已实现的核心功能与高风险修改区域，频率视项目与发布节奏确定。
- 策略：
  - 回归套件分层：快速回归集（冒烟+关键路径）、完整回归集（覆盖主要模块）、专项回归集（针对改动范围）。
  - 自动化优先：优先将稳定且频繁执行的用例自动化。
- 执行时机：缺陷修复后、版本集成时、发布前定期执行。

回归与冒烟的实践要点：
- 用例维护：保持用例与产品变化同步，定期清理陈旧或低价值用例。
- 优先级划分：根据业务影响与出错概率确定用例优先级，优先保证高价值用例自动化。
- 环境一致性：确保测试环境与线上或预发布环境尽可能一致（数据与配置）。
- 报告与反馈：执行后及时生成报告并将失败用例与截图/日志贴到缺陷单或协作平台。

示例流程：
1. CI构建成功 -> 自动化冒烟执行（若通过）-> 触发完整回归或继续人工测试。
2. 若冒烟失败 -> 暂停发布 -> 开发修复 -> 执行回归验证。

小贴士：
- 冒烟集要尽可能短小（10-30条），覆盖最重要路径。
- 回归自动化的投入要结合团队发布频率与维护成本评估，不盲目扩大。
